## Which build, and which IMP modules

**None of IMP.** The wheel is the IMP-free core (PRD-137, `standalone/CMakeLists.txt`), the same
build as the native `imp-bff` wheel. It installs `IMP/bff/` as a namespace portion of `IMP`, so
`import IMP, IMP.bff` works and `IMP.bff.get_build()` is `"core"`.

Why not IMP's kernel plus algebra and friends: everything the web hosts name is in the core. A grep
of `chisurf/core` for `_bff.*` / `IMP.bff.*` shows `GraphPort`, `get_session`, `FitDataset`,
`FitMinimizer`, `FitObjective`, `FitChiSquared`, the `Inference*` factor graph, the spectrum and
photophysics nodes, `MCMCSampler` and `ModelSearch*`. ndXplorer goes through chisurf only
(`chisurf.core.fitting.parameter`, `parameter_group_registry`, `models.parse`, `data.DataCurve`).
None of these is in the connection layer (`src/imp/`, the list in `src/imp/Headers.cmake`). The
layer's IMP modules (kernel, algebra, display, score_functor, core, container, atom, em, rotamer,
PRD-139) would add Boost-heavy compiled code and SWIG `.i` dependencies for no caller in a page.

The bff module source is canonical in the `imp.bff` repository. `imp/modules/bff` is a symlink to
it (`../chisurf/okf/references/imp-ecosystem.md`).

## Dependencies

| Dependency | What the core uses | In the wasm build |
|---|---|---|
| Boost 1.83 | headers only: random, math special functions, histogram, range | the emscripten-ports header archive, `tools/pyodide/wasm_deps.sh` -> `~/opt/wasm-deps` |
| Eigen 3.4.0 | headers | installed by its own CMake there, so `find_package(Eigen3 CONFIG)` works |
| cereal 1.3.2 | headers | copied there, found by header |
| ptolib + codecs | vendored (`thirdparty/ptolib`) | builds unchanged |
| python-ihm parser | vendored C | builds unchanged |
| numpy | C API headers | the cross numpy (`NPY_SIZEOF_LONG 4`), which pyodide-build links into the isolated build env |
| SWIG | host tool | the `swig` wheel from `[build-system]` (4.5.0) |
| tttrlib | not linked | the standalone core has no `IMP_BFF_HAS_TTTRLIB`; the parameter layer does not need it. The tttrlib wheel is loaded beside this one because the page loads it, not because this one links it |

No compiled Boost library, no RMF, HDF5, FFTW, GSL, CGAL, OpenCV or MPI. `find_package` is kept off
the build host's prefixes. scikit-build-core sets `CMAKE_FIND_ROOT_PATH_MODE_PACKAGE=BOTH` when it
cross-compiles, and the first build used exactly that to pick up `~/mambaforge`'s `BoostConfig` and
cereal config, with the host include directory on the wasm compile line. The override puts it back
to `ONLY`. `WASM_LIBRARY_DIR`, which pyodide-build's toolchain file puts first on
`CMAKE_FIND_ROOT_PATH`, points the search at `~/opt/wasm-deps`.

## What the wasm build turns off, and how

It uses one `[[tool.scikit-build.overrides]]` block in `pyproject.toml`, selected by the `PYODIDE=1`
that pyodide-build exports. The block appends to the native `cmake.args`. Three of the switches are
new CMake options in `standalone/CMakeLists.txt`. Their defaults leave the native builds as they
were, which was checked by configuring with defaults: SHARED, OpenMP found, and the `imp_bff_exe`
target present.

| Setting | Why |
|---|---|
| `IMPBFF_LIBRARY_TYPE=STATIC` (new, default `SHARED`) | The core is linked into `_IMP_bff`, so the wheel ships one side module and not two that the browser's loader would have to pair. A STATIC core is not installed. |
| `IMPBFF_WITH_OPENMP=OFF` (new, default `ON`) | Pyodide has no threads. The option skips the search, so the pragmas are comments by decision. `built_with_openmp()` reports it. |
| `IMPBFF_WITH_GPU=OFF` (existing) | This compiles the `dlopen` door out of `ComputeBackend.cpp`. |
| `IMPBFF_COMMAND_LINE=OFF` (new, default `ON`) | There is no command line in a page. The `imp_bff` program would be a `.js` nobody runs. |
| `CMAKE_FIND_ROOT_PATH_MODE_PACKAGE=ONLY` | See *Dependencies*. |
| `install.strip=false` | Keeps emscripten's link output as is. |

Pinned versions are tttrlib's: Pyodide 0.28.0, emscripten 4.0.9 (read back from the cross-build
environment), Python 3.13, and pyodide-build 0.30.9. pyodide-build 0.39 writes a platform tag that
Pyodide 0.28's micropip rejects. The toolchain lives in `~/opt`: `pyodide-venv`, `emsdk`,
`pyodide-xbuildenv`, `pyodide-node`, and the new `wasm-deps`. A clean build takes 3 min 45 s on an
M-series Mac.

### Against native

`port_checks.py` was run natively against (a) a native standalone build of the same commit
(`build/native-arm64`) and (b) the IMP-module build in `~/dev/imp/cmake-build-arm64`, read only.
All 56 values are identical in both comparisons. The only differences are `build`
(`core`/`imp`), `version` and the import path.

The pytest lane under Pyodide (`tools/pyodide/run_tests.mjs`, whole `test/`) gave 1398 passed and
41 failed. Natively the result was 1458 passed and 34 failed, with the same missing-data and
missing-tttrlib-source failures on both sides. The native run also has 57 errors from the program
tests, which that build did not compile. Seven failures occur only in wasm:

| Test | Cause |
|---|---|
| `test_minimizer` parity x3 (atol 1e-12/1e-14 against scipy's `leastsq`) | **FMA contraction, not wasm.** On the rational probe, the wasm result differs from native by 1 ulp. A native build with `-ffp-contract=off` gives bit-for-bit the wasm answer. Clang on arm64 fuses `a*b+c` by default, and wasm has no fused multiply-add. The exact-parity tests hold only where the reference and bff make the same contraction choices. |
| `test_maxent` `seed3-nu1e-05` | The same class: relative difference 1.3e-12 against a 1e-12 bar. |
| `test_compute_backend` x2 | The test starts a subprocess, and emscripten has no processes. The feature is off in this build anyway. |
| `test_data_registry` x2 | `fetch_data` imports `pooch`, which is not in Pyodide (Open 3). |

No test reached a thread spawn that failed. Pyodide reports one hardware thread, so the
`std::thread` pools take their serial path.

### 32-bit review (the tttrlib size_t class)

tttrlib's wasm build found macro times held in `size_t`. The equivalent risks here were checked
directly:

- The integer store is `long long` / `std::vector<long long>` throughout, including the SWIG
  `VectorInt64`. The 2^32+1, 2^40, 2^53+1 and -2^62 round trips are exact.
- The port uid is built from two `uint64_t`.
- `sha256_hex` keeps the bit length in `unsigned long long`.

`long` is used for element counts and grid strides (`OccupancyGrid`, `DiffusionSolverKrylov`,
`TrajectoryAnalysis`). On wasm32 it is 32 bits. That is only wrong past 2^31 elements, which a
32-bit address space cannot hold anyway. `TrajectoryIO` holds file positions in `size_t`, which
limits DCD files to 4 GB in the browser. No 64-bit quantity was found narrowed. As with tttrlib,
that is the result of a grep plus the full lane, not an audit of every kernel.

## Open

1. **CI.** Nothing builds the wasm wheel yet. The job would be `build_wheel.sh` on ubuntu, then
   `smoke_test.mjs`.
2. **The page.** `ndxplorer.app.web --wheels dist/pyodide/imp_bff-*.whl` is the intended door.
   chisurf's core imports `chimol` at module level (`fio/trajectory`,
   `fio/structure/coordinates.py`) and `lzma` (`fio/__init__.py`), and ndXplorer's bundle ships
   neither. Without them the curve fit reports "ChiSurf fitting is not available: No module named
   'chimol'". Tests that pass alone do not show this; the smoke test mounts `~/dev/chimol` and
   loads `lzma` to get past it. The fix belongs to the page (chisurf/ndxplorer): add `chimol` to
   the archive and `lzma` to `PYODIDE_PACKAGES`, or make those imports lazy.
3. **`fetch_data` in a page.** It needs `pooch`, and in a browser it would need `pyodide.http`.
   The wheel's metadata still declares `pooch`. Harmless under `loadPackage`, but
   `micropip.install` would try to resolve it.
4. **Size.** The wheel is built `-O3` like the native one. `-Os` is untried. The 2.4 MB of `data/`
   could be dropped for a parameter-only page.
